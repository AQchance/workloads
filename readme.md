## 2026-05-08

- 现在考虑是否可以将Bi-LSTM和transformer结合起来使用，使用注意力增强的Bi-LSTM来建模时间序列的干扰，传统的Bi-LSTM并不擅长建模长距离的依赖关系，早期的查询干扰需要经过多个时间步才能传递到当前的查询上面来，虽然LSTM的门控机制能缓解梯度消失，但是仍然存在“信息蒸发”的问题，导致远距离的强干扰查询（例如序列开头的I/O密集型查询）对当前查询的影响被弱化了，而注意力机制可以直接捕捉到当前序列中所有时间步的感叹绕查询，并且根据它们与当前查询的相关性来分配不同的权重，这样就可以更有效地建模长距离的依赖关系，从而提升模型对查询干扰的建模能力。
原生 Bi-LSTM 倾向于认为距离目标查询越近的干扰越重要 。但在数据库负载中，干扰强度取决于资源竞争类型而非提交顺序。一个 10 秒前提交的长查询对现在的干扰，可能远大于 1 秒前提交的短查询，LSTM 很难跳出“时序临近”的直觉偏置 。

- 当前已有的创新点总结如下：
  1. 将环境从单机环境迁移到分布式htap环境，建模分布式系统中的查询干扰。
  2. 使用注意力增强的Bi-LSTM来建模时间序列的干扰，提升模型对长距离依赖关系的建模能力。这里应该着重考虑一下多头注意力机制，例如可以建模CPU、磁盘I/O等不同的资源争抢的干扰
  3. 特征提取这里也需要有一些比较新颖的提取方法，应该结合分布式的特征、TiDB这种异构HTAP架构的特征以及一些比较经典的查询计划树的特征来进行提取。
  4. 将建模的粒度从查询级别细化到分片级别，建模分布式系统中的资源争抢和木桶效应。
  5. 设计一个贪心调度算法来利用模型的预测结果进行调度决策，提升系统的整体性能。

- 从模型设计这个角度来看：

  1. 特征层：提出 HTAP-Query-Embedding，利用 Transformer 捕捉行存引擎与列存引擎之间异构的资源需求。
  2. 模型层：构建 Bi-LSTM + Cross-Query Transformer 架构。Bi-LSTM 负责建模分布式环境下的指标漂移（Drift），Transformer 负责建模多个计算节点（TiDB Server）之间的并发资源冲突。
  3. 目标层：根据自己的系统架构设计新的损失函数，专门针对分布式系统中的长尾延迟进行加权优化。

阅读了三篇论文（Stage、Lamba、ICONQ），结合当前 TiDB HTAP 分布式数据库的场景，梳理了 GNN 建模 + LSTM 调度两个层面的创新思路。

### 背景：TiDB HTAP 架构的特殊性

TiDB 的 HTAP 架构比 MPP-only 的分布式数据库（Redshift/Greenplum/AnalyticDB）多了一层建模复杂度：**三套异构资源池**。

| 资源池 | 引擎 | 角色 | 资源特征 | 瓶颈点 |
|--------|------|------|---------|--------|
| TiDB Server | 协调节点 | 顶层 Join/Agg/Sort | 内存（中间结果、Hash Table） | OOM / spill-to-disk |
| TiKV | 行引擎 | 行存扫描、Coprocessor 下算 | CPU(协处理器计算) + 磁盘IO(行存随机读) | 大范围扫描 |
| TiFlash | 列引擎（MPP） | 列存扫描、MPP Join/Agg | CPU(并行计算) + 磁盘IO(列存顺序读) + 网络(Exchange) | segment 间数据传输 |

**三篇论文的盲区**：

- **Lamba**：假设所有 segment 同构（都是 AnalyticDB 计算节点），只建模数据分布差异，不区分引擎。
- **ICONQ**：DBMS 作为黑箱，完全不区分引擎类型和资源池。
- **Stage**：单集群计算节点，无分布式多引擎概念，查询特征化为 33 维扁平向量。

**我们的场景是第一次需要同时建模：行引擎 + 列引擎 + 跨引擎协同 + 分布式 segment 数据倾斜 + 并发调度**。

---

### 创新点一：GNN 层面的双引擎异构图表征

#### 1.1 扩展节点类型（当前仅 operator 一类 → 六类异构节点）

借鉴 Lamba 的异构图表征思路，将执行计划图从单一 operator 节点扩展为六类：

```
节点类型：
  ├── TableScan(TiKV)       — 行引擎扫描节点
  ├── TableScan(TiFlash)    — 列引擎扫描节点
  ├── CopOperator(TiKV)     — TiKV coprocessor 算子（Selection/Projection/TopN 等）
  ├── MPPOperator(TiFlash)  — TiFlash MPP 算子（HashJoin/Agg/ExchangeSender/Receiver）
  ├── ExchangeOperator      — 数据传输节点（跨 segment / 跨引擎）
  └── TiDBServerOperator    — 协调节点顶层算子（HashJoin/Sort/Agg/TopN）
```

各类节点独有特征：

| 节点类型 | 独有特征 | 共同特征 |
|---------|---------|---------|
| TiKV TableScan | NDV、行宽、数据页数、是否主键扫描、coprocessor 下推算子数 | estRows |
| TiFlash TableScan | 列宽、列段数、MPP 分区数、是否启用 delta 层 | estRows |
| Exchange | 数据传输方向（TiKV→TiDB / TiFlash→TiDB / TiFlash↔TiFlash）、传输模式（Hash/Broadcast/Gather） | estRows |
| TiDB Server | 算子类型、预估内存、是否可能触发 spill-to-disk | estRows |

#### 1.2 边特征增加跨引擎数据流语义

```
边的类型：
  ├── same-engine:  TiKV→TiKV 或 TiFlash→TiFlash（引擎内数据流）
  ├── cross-engine: TiKV→TiDB 或 TiFlash→TiDB（引擎→协调节点）
  ├── exchange:     TiFlash→ExchangeReceiver→TiFlash（MPP segment 间传输）
  └── hybrid-join:  两边来自不同引擎的 Join 边 ← TiDB HTAP 特有
```

边特征：预估数据传输字节数（estRows × avg_width）、跨引擎标志位、Exchange 类型 one-hot。

#### 1.3 双引擎分离编码 + Cross-Engine 融合（GNN 核心架构创新）

类似 Lamba 的两阶段设计，但改为按引擎分离而非按 segment 分离：

```
Stage I: Engine-Specific Encoder（引擎内编码）

  TiKV 子图编码器：                    TiFlash 子图编码器：
  ┌──────────────────────┐            ┌──────────────────────────────┐
  │ TiKV Scan → Cop → ...│            │ TiFlash Scan → MPP Join →    │
  │ (GATv2Conv + 残差)   │            │ Exchange → MPP Agg           │
  │ → kv_emb (128 dim)   │            │ (GATv2Conv + 残差)           │
  │ 输出 per-engine res: │            │ → tf_emb (128 dim)            │
  │ [cpu, mem, disk, 0]  │            │ 输出 per-engine res:         │
  └──────────────────────┘            │ [cpu, mem, disk, net_io]     │
                                      └──────────────────────────────┘

Stage II: Cross-Engine Interactor（跨引擎交互编码）

  kv_emb ──┐
            ├── Cross-Attention → hybrid_emb (128 dim)
  tf_emb ──┘
            │
            ├── 学习 TiKV 侧和 TiFlash 侧之间的依赖关系
            │   例：TiFlash 产生大量中间结果 → TiDB Server 内存压力增大
            │
            └── 预测 TiDB Server 部分的资源消耗 (cpu, mem)

Stage III: Global Readout（融合读出）

  kv_emb + tf_emb + hybrid_emb →
    Gate / Max / Sum Pool →
      final_plan_emb (128 dim)
      + 4×3 = 12 dim per-engine resource profile:
        - TiKV:      [cpu, mem, disk_io, 0]
        - TiFlash:   [cpu, mem, disk_io, net_io]
        - TiDB Server: [cpu, mem, 0, 0]
      + 4 dim 总量 resource profile
```

**关键收益**：
- 可以独立预测"TiKV 部分的资源"和"TiFlash 部分的资源"
- Cross-Engine Interactor 显式建模行/列引擎的协同依赖
- 对纯 TiKV 或纯 TiFlash 的查询，另一侧编码自然退化到接近零
- 比 Lamba 的同构 segment 编码更适配 HTAP，比 Stage 的 33 维扁平向量丰富得多

### 创新点二：LSTM 调度层的多引擎资源感知

ICONQ 的 LSTM hidden state 是黑箱式的单一系统状态。我们利用 GNN 输出的 12 维 per-engine 资源画像，做**显式的多资源池追踪**。

#### 2.1 显式多引擎资源状态 H

```
ICONQ:   H ∈ R^256 （黑箱 hidden state）
我们的方案: H = [H_tidb | H_tikv | H_tiflash]

  每个 H_engine 显式维护该引擎的：
    - CPU 可用率（已消耗/总量）
    - 内存可用量
    - IO 带宽可用率
    - 网络带宽可用率（TiFlash 关键）

  查询提交时: H_new = H_old - resource_profile(Q)
  查询完成时: H_new = H_old + resource_profile(Q)
```

**优势**：
- **可解释性**：可以看出每次调度决策背后的资源约束
- **泛化性**：即使并发度/查询模板未见过，物理资源约束依然成立
- **支持引擎互补调度**（见 2.2）

#### 2.2 引擎互补的贪心调度

ICONQ 的评分函数只考虑"查询间是否会拖慢彼此"。我们增加**引擎互补维度**：

```
Score = Δ1(runtime_diff)           ← ICONQ 原有：当前提交 vs 延迟提交
      + Δ2(resource_interference)  ← ICONQ 原有：对已运行查询的影响
      + Δ3(engine_complementarity) ← 新增：引擎互补评分
      - λ × queuing_time

引擎互补评分 Δ3：
  当前 TiFlash CPU 用满 + TiKV 空闲：
    候选 A：CPU 密集 TiFlash 查询 → score += penalty（同引擎争抢）
    候选 B：纯 TiKV 扫描查询    → score -= bonus（引擎互补，零竞争）
  → 优先提交候选 B，同时利用两个引擎
```

这在 HTAP 场景下特别有价值：OLAP 和 OLTP 查询天然使用不同引擎，ICONQ 的黑箱视角完全无法捕捉这一维度。

#### 2.3 Cross-Query Exchange 竞争感知

分布式数据库的隐蔽资源瓶颈：

```
查询 A 的 TiFlash MPP Exchange 正在占用 segment 间网络带宽
查询 B 恰好也需要 MPP Exchange
→ 网络成为瓶颈，两个查询同时变慢
→ 单看每台 segment 节点负载不高，但整体性能骤降
```

通过显式追踪 TiFlash 网络 IO 资源水位，LSTM 可以预测跨查询 Exchange 竞争。这是 ICONQ 和 Lamba 都无法做到的。

### 整体架构对照

```
                  ICONQ                      我们的方案
查询编码：   扁平向量(64+N dim)        GNN 双引擎编码 → 128D emb + 12D res
系统状态：   黑箱 LSTM hidden state    显式多引擎资源池 H
交互建模：   向量直接拼接               Cross-Attention(跨引擎) + Self-Attention(跨查询)
调度粒度：   单一 runtime 评分          4 维资源感知 + 引擎互补评分
数据库类型： 单机 OLAP                 分布式 HTAP（TiKV + TiFlash + TiDB Server）
```

### 三层次创新总结

| 层次 | 创新点 | 对标论文的改进 |
|------|--------|--------------|
| **GNN 编码** | 六类异构节点 + 双引擎分离编码 + Cross-Engine Attention，输出 per-engine 资源画像 | 比 Stage 扁平向量更结构化、比 Lamba 同构 segment 更适配 HTAP、比 ICONQ 黑箱更透明 |
| **LSTM 调度** | 显式多引擎资源池状态跟踪 + 引擎互补贪心调度 + Cross-Query Exchange 竞争感知 | 比 ICONQ 隐式 hidden state 更可解释、更泛化、更适配 HTAP |
| **整体框架** | 第一次在分布式 HTAP 场景做"资源感知的并发查询调度" | 同时覆盖 Stage（单机层次化）+ Lamba（单查询分布式）+ ICONQ（单机并发）三者的盲区 |

### 分布式建模深度分析：Stage 与 Lamba 的可借鉴设计

进一步深入对比后发现，之前的方案在分布式建模上仍有不足。以下是 Stage 和 Lamba 中与分布式直接相关的设计要点，以及我们当前的缺失项。

#### Stage 中的分布式设计

Stage 面向 Redshift（MPP 架构），分布式特征的处理较为间接：

**1. 系统特征向量（Section 4.4）**：Global Model 在 GCN 输出后拼接系统级特征：

```
GCN plan embedding ⊕ [query plan 摘要, instance type, 节点数量, 内存大小, 并发查询数]
                         ↓
                      MLP → runtime 预测
```

启示：TiDB 的集群拓扑信息（TiKV 节点数、TiFlash 节点数、各节点 CPU/内存配置）应该显式注入 GNN 编码层，而不只是放在 LSTM 中隐式追踪。

**2. 不确定性驱动的层次路由**：Local Model 不确定时 fallback 到 Global Model。在分布式场景下，对数据倾斜/Exchange 竞争敏感的查询天然具有更高的预测不确定性，可以触发更重的模型处理。

#### Lamba 中的分布式设计（核心参考）

Lamba 是目前对分布式特征建模最深的论文，有五个关键设计我们尚未纳入：

**1. Per-Segment 数据分布特征（Section 3.1）**

Lamba 在每个 segment 上独立采集特征——因为同一张表在不同 segment 上的行数、页数、属性值分布是不同的（数据倾斜）：

```
每个 segment 节点上：
  ├── 每个属性的值分布直方图（连续列：32-bin 归一化直方图）
  ├── 每个属性的 Top-K 频率（离散列：SpaceSaving 摘要）
  ├── 表级：页数、行数（per-segment，分区不同则不同）
  └── 环境时间序列：过去 6 分钟的 CPU/内存/IO/磁盘（每分钟 1 点）
```

Lamba Fig.18 展示了极端数据倾斜案例：IMDB 的 `cast_info` 表全部集中在 segment 14 上。

**我们缺失的**：目前只有全局 NDV 和表级统计，无法感知"数据在 segment 间的分布是否均匀"。对于 TiFlash MPP 查询，数据倾斜直接导致某些 segment 成为瓶颈。

**2. Per-Segment 计划嵌入（Section 3.2.1）**

同一查询计划 P 在 h 个 segment 上独立编码 h 次——参数共享但输入特征不同，输出不同：

```
Segment 1: GCN(P) + CrossAttn(data_dist_1) + Trans(env_1) → s₁
Segment 2: GCN(P) + CrossAttn(data_dist_2) + Trans(env_2) → s₂
...
Segment h: GCN(P) + CrossAttn(data_dist_h) + Trans(env_h) → sₕ
```

**我们缺失的**：当前 GNN 对整个计划只编码一次，丢失了"不同 segment 执行同一计划但计算负载不同"这个关键维度。

**3. 跨 Segment 的分布式算子建模（Section 3.2.2，Lamba 最大创新）**

用 Self-Attention 模拟 redistribution/broadcast/gather 之后的数据分布变化：

```
原始 segment embeddings:     S = [s₁, s₂, ..., sₕ]
                                   ↓
Self-Attention(S, S, S):     S' = [s'₁, s'₂, ..., s'ₕ]
                                   ↓
Max-Pooling:                  s' = max(s'₁, s'₂, ..., s'ₕ)
                                   ↓
MLP → latency
```

Lamba Fig.7 的典型案例：redistribution 操作导致数据重新倾斜，attention weight 从 segment B 转移到 segment A——Self-Attention 自动捕捉了这种数据迁移效应。

**对应 TiDB 场景**：TiFlash MPP 的 Exchange 算子（Hash/Broadcast/PassThrough）正是 redistribution 的等价物。ExchangeSender→ExchangeReceiver 之间发生数据重分布，目标 segment 可能成为新瓶颈。

**4. 木桶效应的 Max-Pooling 读出**

整体延迟由最慢的 segment 决定。这不是实现细节，而是一个需要显式建模的结构先验。

我们目前的混合读出（max + gate + sum）是针对**执行计划中的算子节点**维度做的，而不是针对 **segment 维度**。两者完全不同：

```
我们目前：          max/mean/sum over plan operator nodes → 128D plan_emb
Lamba：             先 per-segment 编码，再 max over segments → segment-aware emb
```

**5. Segment 数量泛化**

Lamba 的 Self-Attention 参数矩阵大小只与嵌入维度相关，与 segment 数量无关。因此可以在 16-segment 上训练，在 4/8/32-segment 上推理。对 TiDB 的弹性扩缩容场景有意义。

#### 综合差距评估

| 分布式特征 | Stage | Lamba | 我们目前 | 需要补？ |
|-----------|-------|-------|---------|---------|
| 查询计划的图结构编码 | GCN | GCN | GATv2Conv | ✅ 已有 |
| 系统配置信息（节点数/内存等）| ✅ 系统特征向量 | ✅ 环境特征 | ❌ 仅 LSTM 隐式追踪 | ⚠️ 应补入 GNN 层 |
| Per-segment 数据分布 | ❌ | ✅ 属性直方图 per-segment | ❌ 只有全局 NDV | 🔴 需要补 |
| Per-segment 计划编码 | ❌ | ✅ h 次独立编码 | ❌ 只编码一次 | 🔴 需要补 |
| 分布式算子（Exchange/Redistribute）| ❌ | ✅ Self-Attention 模拟 | ⚠️ 仅在边类型标记 | 🟡 需要深化 |
| 木桶效应（max-pooling over segments）| ❌ | ✅ | ❌ 只有节点级 pooling | 🔴 需要补 |
| 环境时间序列（CPU/内存/IO）| ❌ | ✅ Transformer 编码 | ❌ 未采集 | 🟡 视数据可得性 |
| Segment 数量泛化 | ❌ | ✅ | ❌ | 🟡 弹性扩缩时可做 |
| 跨引擎异构（TiKV≠TiFlash）| ❌ | ❌ | ✅ 双引擎分离 | ✅ 核心创新 |

### 完善方案：Lamba 风格的三阶段 Per-Segment 编码

将 GNN 按 Lamba 的思路重构为面向 TiDB HTAP 的三阶段架构：

```
Stage I: Per-Engine Per-Segment 编码（最底层，数据分布感知）

  ┌─ TiKV Segment 1 ─┐   ┌─ TiKV Segment 2 ─┐       ┌─ TiKV Segment k ─┐
  │ GNN_kv(plan)      │   │ GNN_kv(plan)      │  ...  │ GNN_kv(plan)      │
  │ + data_dist_kv_1  │   │ + data_dist_kv_2  │       │ + data_dist_kv_k  │
  │ + env_kv_1        │   │ + env_kv_2        │       │ + env_kv_k        │
  │ → seg_emb_kv₁     │   │ → seg_emb_kv₂     │       │ → seg_emb_kvₖ     │
  └───────────────────┘   └───────────────────┘       └───────────────────┘

  ┌─ TiFlash Segment 1 ─┐ ┌─ TiFlash Segment 2 ─┐     ┌─ TiFlash Segment m ─┐
  │ GNN_tf(plan)        │ │ GNN_tf(plan)        │ ... │ GNN_tf(plan)        │
  │ + data_dist_tf_1    │ │ + data_dist_tf_2    │     │ + data_dist_tf_m    │
  │ + env_tf_1          │ │ + env_tf_2          │     │ + env_tf_m          │
  │ → seg_emb_tf₁       │ │ → seg_emb_tf₂       │     │ → seg_emb_tfₘ       │
  └─────────────────────┘ └─────────────────────┘     └─────────────────────┘

  说明：
  - GNN_kv 和 GNN_tf 是结构相同但参数独立的 GATv2Conv 编码器
  - data_dist 是 per-segment 的数据分布特征（见下文"可行性评估"）
  - env 是 per-segment 的环境时间序列（Prometheus 采集）
  - 参数在同类 segment 间共享，但输入不同 → 输出不同


Stage II: Per-Engine 段内交互（Exchange/Redistribution 模拟）

  TiKV Segments:
    Self-Attention([seg_emb_kv₁, seg_emb_kv₂, ..., seg_emb_kvₖ])
    → [seg'_kv₁, ..., seg'_kvₖ]
    → Max-Pooling（木桶效应）→ engine_emb_kv + engine_res_kv

  TiFlash Segments:
    Self-Attention([seg_emb_tf₁, ..., seg_emb_tfₘ])
    → [seg'_tf₁, ..., seg'_tfₘ]
    → Max-Pooling（木桶效应）→ engine_emb_tf + engine_res_tf

  说明：
  - Self-Attention 参数矩阵大小只与嵌入维度相关，与 segment 数量无关
    → 可以在 k 个 TiKV/m 个 TiFlash 上训练，在不同数量上推理
  - TiKV 通常不需要 Exchange（无 MPP），Self-Attention 可能退化为
    简单 pooling，但保留这个结构可以让模型自行学习
  - TiFlash 的 Self-Attention 直接对应 MPP Exchange 的数据重分布效应


Stage III: 跨引擎融合 + TiDB Server 预测

  engine_emb_kv ──┐
                  ├── Cross-Attention → hybrid_emb
  engine_emb_tf ──┘
                  │
                  ├── 学习 TiKV/TiFlash 之间的依赖关系
                  │
                  └── MLP → TiDB Server 部分资源 + 最终资源画像

  最终输出：
    - final_plan_emb (128 dim)：融合了 per-segment 分布式信息的执行计划向量
    - 12 dim per-engine resource profile：
        TiKV:      [cpu, mem, disk_io, 0]
        TiFlash:   [cpu, mem, disk_io, net_io]
        TiDB Server: [cpu, mem, 0, 0]
    - 4 dim 总量 resource profile

  与后续 LSTM 调度的接口不变：
    plan_emb(128) + resource_profile(4 dim per-engine total)
    → Bi-LSTM 显式多引擎资源追踪 → 贪心调度
```

#### 三阶段设计的优势

1. **完整覆盖 Lamba 的分布式建模能力**：per-segment 数据感知 + 段间 Self-Attention 交互 + Max-Pooling 木桶效应
2. **同时保留双引擎异构建模**：TiKV 和 TiFlash 在 Stage I/II 分离处理，Stage III 融合
3. **自然的退化能力**：纯 TiKV 查询只有 kv 分支有信号（TiFlash 侧接近零），纯 TiFlash 查询同理，HTAP 混合查询两个分支都有信号
4. **Segment 数量泛化**：Self-Attention 只依赖嵌入维度，可在不同规模集群上迁移
5. **与 ICONQ LSTM 调度层的接口不变**：GNN 仍输出 `plan_emb(128) + resource_profile`

#### Per-Segment 数据分布特征的可行性评估

关键问题：TiDB 能否提供 Lamba 依赖的 per-segment 特征？

| Lamba 需要的特征 | TiDB 对应能力 | 可得性 |
|-----------------|-------------|--------|
| 每个 segment 的表行数 | `INFORMATION_SCHEMA.TIFLASH_REPLICA` + PD region 分布 API | 🟡 通过 PD API 可获取每个 store 的 region 数 |
| 每个 segment 的属性值分布 | TiFlash 不直接暴露 per-segment 列统计 | 🔴 难以直接获取 |
| 环境时间序列（CPU/内存/IO）| Prometheus/Grafana（node_exporter + tidb_exporter）| ✅ 已有监控栈可采集 |
| Exchange 算子类型和 actRows | EXPLAIN / EXPLAIN ANALYZE | ✅ 已有 |

**Per-segment 数据分布不可得的替代方案**：

1. **用 Region 分布近似数据分布**：通过 PD HTTP API（`/pd/api/v1/stores` 和 `/pd/api/v1/regions`）获取每个表在不同 TiKV/TiFlash store 上的 region 数量分布，作为 per-segment 数据量的 proxy。

2. **用 estRows ÷ segment_count 估算均匀分布**：当无法获取真实倾斜时，假设均匀分配。对于有明显倾斜的场景，可以在训练时通过 EXPLAIN ANALYZE 的 per-segment actRows 学习倾斜模式。

3. **训练时用 EXPLAIN ANALYZE per-segment actRows 作为 ground truth**：TiDB 的 EXPLAIN ANALYZE 在 MPP 模式下会显示每个 ExchangeReceiver 在各 segment 的实际行数（如 `├─ExchangeReceiver(Build)  │ rows: 1000000(seg0:500000, seg1:300000, seg2:200000)`）。这些 actRows 可用作训练标签来学习数据倾斜对 runtime 的影响，但不能用于推理特征（因为推理时没有 actRows）。

4. **用 NDV 和表级统计作为近似**：对于无法获取 per-segment 特征的列，回退到使用全局 NDV 和表级统计（当前方案已有），并在 GNN 中增加一个"segment skew indicator"特征——用 region 数量的方差来估算数据倾斜程度。
